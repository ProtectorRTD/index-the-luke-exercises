## 1. Идея главы своими словами

**Первичный ключ.** Поиск по первичному ключу — самый простой случай: значение уникально, поэтому база спускается по дереву и читает ровно одну строку. Проход по листьям не нужен. Медленным такой поиск не бывает.

**Составной индекс.** Индекс может состоять из нескольких колонок, например `(customer_id, status)`. Записи в нём отсортированы как в телефонной книге: сначала по первой колонке, при равной первой — по второй. Отсюда главное правило главы:

> Индекс помогает, только если в условии есть **первые** колонки индекса. Это правило левого префикса.

Индекс `(customer_id, status)` подходит для запросов:

- `WHERE customer_id = 17` — по первой колонке;
- `WHERE customer_id = 17 AND status = 'cancelled'` — по обеим.

И почти не подходит для `WHERE status = 'cancelled'`: строки с этим статусом разбросаны по всему индексу, внутри каждого клиента. Найти их можно, только прочитав весь индекс. Это как искать в телефонной книге всех по имени «Ян», не зная фамилии.

**Порядок колонок.** Если запрос сравнивает на равенство все колонки индекса, для **этого** запроса порядок колонок неважен: `(customer_id, status)` и `(status, customer_id)` найдут нужные строки одинаково быстро. Порядок решает, **какие ещё** запросы сможет обслужить тот же индекс. Отсюда рецепт из книги: выбирать порядок так, чтобы один индекс покрыл как можно больше запросов. Совет «ставить первой самую селективную колонку» для равенств — миф.

**Медленные индексы, часть II.** Если для запроса подходят несколько индексов, выбирает планировщик, и выбирает по статистике. Когда статистика устарела или не знает о связи между колонками, он может взять индекс похуже. Поэтому про индекс всегда спрашиваем не «есть ли он», а «какой план выбран и сколько он читает».

**Access и filter предикаты.** Условие, по которому база спускается по дереву и ограничивает прочитанный диапазон индекса, — **access-предикат**. Условие, которое проверяется уже на прочитанных строках, — **filter-предикат**. Access-предикаты уменьшают работу, filter-предикаты только отбрасывают результат.

## 2. Как это выглядит в PostgreSQL

| Книга | Postgres |
| --- | --- |
| `INDEX UNIQUE SCAN` | `Index Scan using orders_pkey` с одной строкой |
| `INDEX RANGE SCAN` | `Index Scan` или `Bitmap Index Scan` по диапазону |
| access-предикат | `Index Cond` |
| filter-предикат на строке таблицы | `Filter` и `Rows Removed by Filter` |
| filter-предикат при bitmap | `Recheck Cond` и `Filter` в `Bitmap Heap Scan` |

Две особенности Postgres, о которых книга не говорит.

**`Index Cond` ещё не значит «правильный доступ».** Postgres (до версии 18) умеет использовать составной индекс даже по условию на **не первую** колонку. В плане при этом честно написано `Index Cond: (customer_id = 17)`, но читается весь индекс от начала до конца, а проверка идёт на каждой записи. Отличить такой случай можно только по числу страниц: `Buffers` будет порядка размера индекса, а не единицы. Это главная ловушка модуля, она есть в заданиях 2.2, 2.3 и 2.5.

В PostgreSQL 18 появился skip scan: он умеет «перепрыгивать» по значениям первой колонки, если их мало. У нас версия 16, и в задании 2.5 вы сделаете то же самое руками.

**Bitmap умеет объединять индексы.** Если есть отдельные индексы по `customer_id` и по `status`, Postgres может прочитать оба, построить две битовые карты и пересечь их (`BitmapAnd`). Это работает, но обычно хуже одного составного индекса: каждый индекс читается по своему условию целиком. По `status = 'delivered'` это 90% таблицы.

## 3. Как читать план: что нового в этом модуле

Сравните два плана одного запроса `WHERE customer_id = 17 AND status = 'cancelled'`.

Индекс только по `customer_id`:

```
Bitmap Heap Scan on orders  (actual rows=12 loops=1)
  Recheck Cond: (customer_id = 17)
  Filter: (status = 'cancelled'::text)
  Rows Removed by Filter: 487
  Buffers: shared hit=494
  ->  Bitmap Index Scan on orders_customer_id_idx  (actual rows=499 loops=1)
        Index Cond: (customer_id = 17)
```

Индекс по `(customer_id, status)`:

```
Index Scan using orders_customer_id_status_idx on orders  (actual rows=12 loops=1)
  Index Cond: ((customer_id = 17) AND (status = 'cancelled'::text))
  Buffers: shared hit=15
```

В первом плане `status` — filter-предикат: прочитано 499 заказов клиента, 487 выброшено. Во втором обе колонки в `Index Cond`, прочитано только то, что нужно.

Вопросы к плану в этом модуле:

1. Все ли условия из `WHERE` попали в `Index Cond`? Что осталось в `Filter`?
2. Сколько строк выброшено фильтром?
3. Соответствует ли число страниц ожиданию? Если `Index Cond` есть, а страниц сотни или тысячи, проверьте, по первой ли колонке индекса идёт условие.
