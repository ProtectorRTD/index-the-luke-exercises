# 2.10. Поиск по первичному ключу, а медленно

**Уровень:** расследование. В чём причина, задание не говорит.

## Сценарий

Теги обращений хранятся в таблице связей `ticket_tags`: одна строка на пару «обращение, тег». Первичный ключ составной, обе колонки входят в него.

Карточка обращения показывает его теги (`a.sql`):

```sql
SELECT tag_id
FROM ticket_tags
WHERE ticket_id = 123456;
```

История клиента показывает его обращения вместе с тегами (`b.sql`):

```sql
SELECT t.id, t.subject, tt.tag_id
FROM tickets t
JOIN ticket_tags tt ON tt.ticket_id = t.id
WHERE t.customer_id = 17;
```

Разработчик уверен, что оба запроса должны быть быстрыми: «мы же ищем по колонке из первичного ключа, а поиск по первичному ключу — самый быстрый». Мониторинг показывает обратное.

`setup.sql` создаёт индекс `tickets (customer_id)`: к поиску обращений клиента претензий нет.

Запросы менять нельзя. На `ticket_tags` можно добавить не больше одного индекса.

## Что сделать

1. `lab reset`, в `lab psql` выполните `\i modules/02-where-equality/tasks/2.10-lookup-by-primary-key/setup.sql`.
2. Найдите причину и сформулируйте её одной фразой.
3. Исправьте в `solution.sql`.
4. `lab check 2.10`.

## Как проверяется

- создано не больше одного индекса;
- `a.sql` читает не больше 10 страниц;
- `b.sql` читает не больше 2 000 страниц, и в его плане нет `Seq Scan` по `ticket_tags`.
