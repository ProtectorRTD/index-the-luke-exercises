# 2.7. Прогноз для составного индекса

**Уровень:** расчёт. Сначала считаем, потом сверяем.

## Сценарий

`setup.sql` создаёт один индекс:

```sql
CREATE INDEX orders_customer_id_status_idx ON orders (customer_id, status);
```

Три запроса обращаются к нему по-разному:

| | Запрос |
| --- | --- |
| A | `SELECT id, total FROM orders WHERE customer_id = 17 AND status = 'cancelled'` |
| B | `SELECT id, total FROM orders WHERE customer_id = 17` |
| C | `SELECT id, total FROM orders WHERE status = 'pending'` |

Заказы клиента 17 разбросаны по всей таблице. Заказы в статусе `pending` тоже.

## Что сделать

1. `lab reset`, в `lab psql` выполните `\i modules/02-where-equality/tasks/2.7-predict-composite/setup.sql`.
2. Соберите исходные числа: сколько страниц в таблице и в индексе, сколько строк возвращает каждый запрос.
3. Для каждого запроса **до запуска** посчитайте, сколько страниц он прочитает. Модель та же, что в задании 1.8: спуск, листья, страницы таблицы.
4. Для запроса C есть два кандидата: прочитать весь индекс и сходить в таблицу за найденными строками либо прочитать таблицу целиком. Посчитайте оба варианта и предскажите, какой выберет планировщик.
5. Проверьте прогнозы: `EXPLAIN (ANALYZE, BUFFERS)`, второй прогон. Впишите в `answers.yaml` фактические числа.

| Ответ | Что это | Допуск |
| --- | --- | --- |
| `table_pages`, `index_pages` | страниц в таблице `orders` и в индексе | точно |
| `a_rows`, `a_buffers` | запрос A | строки точно, страницы 15% |
| `b_rows`, `b_buffers` | запрос B | строки точно, страницы 10% |
| `c_rows` | запрос C | точно |
| `c_node` | каким узлом планировщик читает `orders` в запросе C | как в плане |
| `c_buffers` | запрос C | 5% |

6. `lab check 2.7`.

После PASS ответьте себе: в запросе C планировщик выбрал самый дешёвый по страницам вариант? Если нет, почему?
