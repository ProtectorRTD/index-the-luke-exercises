Индексов в исходной базе нет, кроме первичных ключей. В данных есть перекосы: 60% клиентов из `SK`, 90% заказов в статусе `delivered`, первый 1% клиентов делает половину заказов. Посмотреть таблицу в psql: `\d orders`.

## 2. В каком порядке выполняется SELECT

Пишем запрос в одном порядке, а логически он выполняется в другом:

| Шаг | Часть запроса | Что происходит |
| --- | --- | --- |
| 1 | `FROM`, `JOIN` | Собрать строки из таблиц и соединить их |
| 2 | `WHERE` | Отбросить строки, не подходящие под условие |
| 3 | `GROUP BY` | Разложить строки по группам |
| 4 | `HAVING` | Отбросить группы целиком |
| 5 | `SELECT` | Посчитать выражения и оконные функции |
| 6 | `DISTINCT` | Убрать дубли |
| 7 | `ORDER BY` | Отсортировать |
| 8 | `LIMIT`, `OFFSET` | Отрезать нужный кусок |

Два следствия, на которых спотыкаются чаще всего:

- В `WHERE` нельзя использовать агрегаты (`count(*) > 10`): групп ещё нет. Для этого есть `HAVING`.
- Оконные функции считаются на шаге 5, уже после `WHERE`. Чтобы отфильтровать по результату оконной функции, нужен подзапрос или CTE.

Это логический порядок. Физически Postgres может делать что угодно, если результат тот же: например, применить условие из `WHERE` прямо при чтении таблицы. Физический порядок показывает `EXPLAIN`.

## 3. JOIN

- `JOIN` (он же `INNER JOIN`): только пары строк, для которых выполнено условие `ON`.
- `LEFT JOIN`: все строки левой таблицы. Если пары справа нет, правые колонки равны `NULL`.
- Строк после `JOIN` может стать **больше**: у клиента 500 заказов, значит, после соединения клиентов с заказами он встретится 500 раз. Если потом посчитать `count(*)` по клиентам, получатся заказы, а не клиенты.

## 4. Подзапросы: IN, EXISTS, NOT EXISTS

```sql
-- клиенты, у которых есть заказ дороже 3000
SELECT id FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.total > 3000);
```

Подзапрос внутри `EXISTS` ссылается на внешнюю таблицу (`c.id`). Это **коррелированный** подзапрос: логически он выполняется для каждой строки снаружи. `EXISTS` ничего не размножает: клиент попадёт в результат один раз, сколько бы дорогих заказов у него ни было. В этом отличие от `JOIN`.

`NOT EXISTS` — «нет ни одной строки». Через `NOT IN` так писать опасно: если в подзапросе встретится `NULL`, `NOT IN` вернёт пустой результат.

## 5. CTE и оконные функции

CTE (`WITH имя AS (...)`) — именованный подзапрос. Удобно разбивать длинный запрос на шаги.

Оконная функция считает значение по группе строк, но **не схлопывает** строки, как `GROUP BY`:

```sql
SELECT id, customer_id, total,
       row_number() OVER (PARTITION BY customer_id ORDER BY total DESC) AS rn
FROM orders;
```

`PARTITION BY` — по каким группам считать, `ORDER BY` внутри `OVER` — в каком порядке внутри группы. Полезные функции: `row_number()`, `rank()`, `lag(x)` (значение из предыдущей строки), `sum(x) OVER (ORDER BY ...)` (нарастающий итог).

## 6. LATERAL

`JOIN LATERAL (подзапрос) ON true`: подзапрос справа может ссылаться на колонки таблицы слева и выполняется для каждой её строки. Пример: «по три последних заказа каждого клиента». Подробно понадобится в модулях 8 и 9, здесь просто знать, что так можно.

## 7. Как читать EXPLAIN

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

План — дерево. Каждая строка со стрелкой `->` — узел, его дети с отступом ниже. **Данные текут снизу вверх**: листья читают таблицы, родители соединяют, группируют и сортируют то, что пришло от детей.

```
Aggregate  (cost=25498.64..25498.65 rows=1 width=8) (actual time=70.2..70.2 rows=1 loops=1)
  Buffers: shared hit=11712
  ->  Hash Join  (cost=2681.29..25498.41 rows=93 width=0) (actual time=7.0..70.1 rows=101 loops=1)
        Hash Cond: (o.customer_id = c.id)
        ->  Seq Scan on orders o  (... rows=5000 ...) (actual ... rows=5007 loops=1)
              Filter: (status = 'pending'::text)
              Rows Removed by Filter: 994993
        ->  Hash  (...)
              ->  Seq Scan on customers c  (...)
```

| Что | Где в плане | Как понимать |
| --- | --- | --- |
| Оценка | первые скобки: `cost=начало..конец rows=N` | Сколько строк планировщик **ожидает**. Стоимость в условных единицах |
| Факт | вторые скобки: `actual time=… rows=N loops=K` | Сколько строк узел **реально** вернул за один запуск и сколько раз запускался |
| Всего строк | `rows × loops` | `rows` — среднее за один запуск. При `loops=10` и `rows=507` узел вернул около 5 070 строк |
| Страницы | `Buffers: shared hit=… read=…` | Сумма — сколько страниц по 8 КБ тронул узел **вместе с детьми** |
| Фильтр | `Filter`, `Rows Removed by Filter` | Сколько строк прочитано зря |

Главные вопросы к любому плану:

1. Где больше всего строк и страниц? Там и проблема.
2. Где оценка (`rows` в первых скобках) сильно расходится с фактом? Там планировщик ошибся и мог выбрать плохой план.
3. Какой узел выполняется много раз (`loops`)? Всё, что внутри, умножается на это число.

Основные узлы, которые встретятся в модуле: `Seq Scan` (чтение всей таблицы), `Hash Join` (строит хеш-таблицу по одной стороне и проверяет по ней другую), `Nested Loop` (для каждой строки внешнего узла выполняет внутренний), `HashAggregate` / `GroupAggregate` (группировка), `Sort`, `Limit`. Подробно каждый разбирается в своём модуле книги.
