# 1.7. Где индекс перестаёт быть выгодным

**Уровень:** расчёт и эксперимент.

## Сценарий

`setup.sql` создаёт индекс по дате регистрации:

```sql
CREATE INDEX customers_created_at_idx ON customers (created_at);
```

Клиенты регистрировались равномерно с 2020-01-01 по 2025-12-31, это 2 192 дня. Запрос берёт первые `N` дней:

```sql
SELECT * FROM customers
WHERE created_at >= '2020-01-01'
  AND created_at < timestamptz '2020-01-01' + interval 'N days';
```

При малом `N` планировщик использует индекс. При большом читает таблицу целиком. Где-то между ними граница.

## Что сделать

1. Сначала запишите свою догадку: при какой доле строк планировщик переключится на `Seq Scan`? Распространённое «правило» говорит про 5–10%.
2. `lab reset`, в `lab psql` выполните `\i modules/01-anatomy/tasks/1.7-plan-flip-point/setup.sql`.
3. Найдите наименьшее `N`, при котором план становится `Seq Scan`. Хватит `EXPLAIN` без `ANALYZE`: запрос выполнять не нужно. Делите отрезок пополам, это 11 шагов.
4. Посчитайте, какая это доля строк таблицы в процентах.
5. Повторите поиск с настройкой для SSD: `SET random_page_cost = 1.1;`. После эксперимента `RESET random_page_cost;`.
6. Впишите в `answers.yaml`:
   - `flip_days`: наименьшее `N` с `Seq Scan` при настройках по умолчанию. Допуск 3%.
   - `flip_percent`: доля строк таблицы при этом `N`, в процентах. Допуск 5%.
   - `flip_days_ssd`: наименьшее `N` с `Seq Scan` при `random_page_cost = 1.1`. Допуск 3%.
7. `lab check 1.7`.

После PASS ответьте себе: почему граница оказалась настолько дальше «правила про 5–10%»? Какой узел плана работает прямо перед границей и чем он отличается от `Index Scan`?
