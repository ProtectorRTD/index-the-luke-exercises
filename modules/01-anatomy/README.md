## 1. Идея главы своими словами

Индекс — это отдельная структура рядом с таблицей, где значения колонки лежат **в отсортированном порядке** и у каждого значения есть адрес строки в таблице.

Держать отсортированный массив на диске дорого: каждая вставка двигала бы половину данных. Поэтому индекс устроен из двух частей:

- **Листья.** Маленькие страницы по 8 КБ, внутри каждой записи отсортированы, а сами страницы связаны в двусвязный список. Порядок обеспечивается ссылками, а не физическим расположением. Вставка трогает одну страницу, иногда делит её на две.
- **Дерево над листьями (B-tree).** Внутренние страницы хранят «самое большое значение в каждой странице уровнем ниже». По ним за несколько шагов спускаешься от корня к нужному листу. Дерево всегда сбалансировано: путь до любого листа одинаковой длины.

Дерево очень широкое: в одну страницу помещаются сотни ссылок. Поэтому даже на миллионах строк глубина 3–4 уровня, и она растёт логарифмически: в 1000 раз больше данных означает примерно +1 уровень.

Поиск по индексу состоит из трёх шагов:

1. **Спуск по дереву.** Несколько страниц, всегда быстро.
2. **Проход по цепочке листьев**, если подходящих значений много.
3. **Поход в таблицу** за каждой найденной строкой.

Главная мысль главы: «индекс тормозит» почти никогда не из-за «испорченного» дерева. Медленными бывают шаги 2 и 3: когда под условие попадает много строк, база долго идёт по листьям и делает отдельный поход в таблицу за каждой строкой. Индекс хорош, когда условие выбирает **мало** строк.

## 2. Как это устроено в PostgreSQL

Книга написана для нескольких СУБД. Вот что важно именно для Postgres.

- **Таблица отдельно, индекс отдельно.** Таблица в Postgres называется heap («куча»): строки лежат в страницах в порядке вставки, без сортировки. Любой индекс — отдельный файл. В листе индекса рядом со значением хранится **TID** — адрес строки в виде `(номер страницы, номер строки в странице)`. В Oracle это ROWID, идея та же.
- **Первичный ключ = уникальный B-tree индекс.** Его создаёт `PRIMARY KEY`. Например, `orders_pkey`.
- **Страница = 8 КБ.** Все чтения считаются страницами. В плане это `Buffers: shared hit=… read=…`: hit — страница была в памяти Postgres, read — пришлось просить у ОС. Нам важна их **сумма**: сколько страниц запрос вообще тронул. Время скачет, а сумма страниц от прогона к прогону одинаковая.
- **Три способа прочитать таблицу**, которые встретятся в этом модуле:

| Узел плана | Что делает | Когда выгоден |
| --- | --- | --- |
| `Seq Scan` | Читает всю таблицу подряд и проверяет условие на каждой строке | Когда подходит большая часть строк |
| `Index Scan` | Шаги 1–3: спуск, проход по листьям, поход в таблицу за **каждой** найденной строкой | Когда подходит мало строк |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | Сначала собирает по индексу все адреса и сортирует их по страницам, потом читает каждую нужную страницу таблицы **один раз** | Промежуточный случай: строк много, но не большинство |

- **Кто выбирает.** Планировщик оценивает, сколько строк вернёт условие (по статистике `pg_stats`), и считает стоимость каждого варианта. Если оценка строк сильно ошибается, план будет плохим.
- **`random_page_cost`.** Насколько дороже «прыгнуть» на случайную страницу, чем читать подряд. В нашем стенде стоит значение по умолчанию `4`. На проде с SSD часто ставят `1.1`, и тогда индексы выбираются охотнее. Помните об этом, когда сравниваете с рабочими планами.

## 3. Как читать план: что нового в этом модуле

Запускаем так:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

`ANALYZE` выполняет запрос по-настоящему и показывает фактические числа. `BUFFERS` добавляет число страниц.

```
Index Scan using customers_email_idx on customers  (cost=0.42..8.44 rows=1 width=45) (actual time=0.031..0.032 rows=1 loops=1)
  Index Cond: (email = 'Peter.Oravec0004242@example.cz'::text)
  Buffers: shared hit=4
```

- `Index Scan using <индекс> on <таблица>` — способ доступа.
- `cost=…` — оценка планировщика в условных единицах. `rows=1` в первых скобках — **ожидаемое** число строк.
- `actual … rows=1 loops=1` — **фактическое** число строк и сколько раз узел выполнялся.
- `Index Cond` — условие, по которому идёт спуск по дереву. Это хорошо: база сразу находит нужное место.
- `Filter` и `Rows Removed by Filter` — условие проверяется **после** чтения строки, а прочитанные зря строки отбрасываются. Большой `Rows Removed by Filter` — первый признак, что индекса не хватает.
- `Buffers: shared hit=4` — тронуто 4 страницы. Для поиска одной строки это 3 страницы индекса (дерево глубины 3) и 1 страница таблицы.

## 4. Заглянуть внутрь индекса: pageinspect

Расширение `pageinspect` уже установлено. Три функции, которые нужны в задании 1.2:

```sql
-- метаданные: где корень и сколько уровней над листьями
SELECT root, level FROM bt_metap('orders_created_at_idx');

-- статистика одной страницы: тип (r = корень, i = внутренняя, l = лист), число записей
SELECT type, live_items, btpo_prev, btpo_next FROM bt_page_stats('orders_created_at_idx', 1);

-- содержимое страницы: ключи и ссылки (ctid)
SELECT itemoffset, ctid, data FROM bt_page_items('orders_created_at_idx', 1) LIMIT 5;
```

`level` в `bt_metap` — это число уровней **над** листьями. Глубина дерева, то есть сколько страниц прочитать при спуске, равна `level + 1`.
