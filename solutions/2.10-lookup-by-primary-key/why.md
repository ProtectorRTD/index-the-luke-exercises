# Разбор 2.10

```sql
CREATE INDEX ticket_tags_ticket_id_idx ON ticket_tags (ticket_id);
```

**Причина одной фразой.** Первичный ключ объявлен как `(tag_id, ticket_id)`, а запросы ищут по `ticket_id`: это вторая колонка индекса, спуститься по дереву к нужному обращению нельзя.

«Поиск по первичному ключу быстрый» верно, когда в условии **все** колонки ключа или хотя бы первые. Составной первичный ключ — обычный составной индекс, только уникальный.

## Что было

`a.sql`: `Seq Scan on ticket_tags`, прочитана вся таблица, 5 120 страниц на масштабе `s`, ради одной-двух строк.

`b.sql`: `Hash Join` с полным чтением `ticket_tags`. Для 280 обращений клиента прочитано 944 тысячи строк связей.

## Что стало

`a.sql`: `Index Scan` по новому индексу, 4 страницы.

`b.sql`: `Nested Loop`: для каждого обращения клиента короткий поиск его тегов. Около 1 400 страниц, из них 280 — сами обращения.

## Это свойство всех таблиц связей

Таблица «многие ко многим» используется в обе стороны: «теги обращения» и «обращения с тегом». Первичный ключ обслуживает одно направление, то, чья колонка стоит первой. Для второго направления нужен отдельный индекс. Поэтому у таблицы связей почти всегда два индекса:

```sql
PRIMARY KEY (tag_id, ticket_id)          -- обращения с тегом
CREATE INDEX ... ON (ticket_id)          -- теги обращения
```

Вариант `(ticket_id, tag_id)` тоже проходит проверку. Он чуть больше, зато запросу `a.sql` не нужна таблица: всё есть в индексе. Это тема модуля 7.

Такая же ситуация возникает с внешними ключами: Postgres не создаёт индекс по колонке внешнего ключа автоматически. В нашей схеме нет индекса на `orders.customer_id` и на `order_items.order_id`, пока вы его не создадите. К этому вернёмся в модуле 6.

## Любопытная деталь

Если переписать `a.sql` с соединением с таблицей `tags`:

```sql
SELECT t.name FROM ticket_tags tt JOIN tags t ON t.id = tt.tag_id WHERE tt.ticket_id = 123456;
```

запрос без всякого нового индекса читает около 60 страниц. Планировщик перебирает все 20 тегов и для каждого ищет пару `(tag_id, ticket_id)` в первичном ключе: двадцать точных поисков по полному ключу. Это тот же ручной skip scan, что в задании 2.5, только планировщик нашёл его сам, потому что соединение дало ему список значений первой колонки.

## Ловушки

- **Индекс по `tag_id`.** Эта колонка и так первая в первичном ключе, индекс дублирует его префикс.
- **Индекс `(tag_id, ticket_id)`.** Точная копия первичного ключа.
