# Разбор 2.8

```sql
CREATE INDEX tickets_status_assignee_priority_idx ON tickets (status, assignee_id, priority);
CREATE INDEX tickets_customer_id_status_idx ON tickets (customer_id, status);
```

## Как к этому прийти

Выпишем колонки каждого запроса:

| Запрос | `assignee_id` | `status` | `priority` | `customer_id` |
| --- | --- | --- | --- | --- |
| `t1` | да | да | | |
| `t2` | да | да | да | |
| `t3` | | да | да | |
| `t4` | | | | да |
| `t5` | | да | | да |

Группа `t4`–`t5` — это задание 2.2: `customer_id` есть в обоих запросах, он первый. Индекс `(customer_id, status)`.

В группе `t1`–`t3` на три запроса остаётся один индекс. Правило из главы: индекс работает, когда в запросе есть его первая колонка. Колонка, которая есть во всех трёх запросах, — `status`. Значит, он первый.

## Сравнение вариантов, масштаб `s`

| Первый индекс | `t1` | `t2` | `t3` | Всего с `(customer_id, status)` |
| --- | --- | --- | --- | --- |
| `(status, assignee_id, priority)` | 268 | 13 | 317 | около 900 |
| `(status, priority, assignee_id)` | 277 | 13 | 308 | около 900 |
| `(assignee_id, status, priority)` | 264 | 13 | 740 | около 1 320 |
| `(priority, status, assignee_id)` | 702 | 13 | 302 | около 1 320 |

`t2` задаёт все три колонки, ему порядок безразличен. Разница в запросе, которому не хватает первой колонки: он читает индекс целиком.

**Почему два варианта со `status` впереди почти равны.** Возьмём `(status, assignee_id, priority)` и запрос `t3`, где нет `assignee_id`. Postgres спускается к участку `status = 'open'` и читает его весь, проверяя `priority`. Открытых обращений 2%, участок занимает пару десятков страниц. Это тот же «пропуск колонки», что был провалом в задании 2.2, но здесь он дешёвый: пропускается не весь индекс, а маленький его кусок.

Отсюда уточнение правила: важна не только первая колонка, но и то, **насколько сужает поиск префикс, который в запросе есть**.

## Про миф о селективности

`status` — наименее селективная колонка из трёх: у него четыре значения, у `assignee_id` сорок. Совет «ставьте первой самую селективную» дал бы `(assignee_id, ...)` и счёт на 45% хуже. Порядок колонок определяют запросы, а не число разных значений. Отдельно этот миф проверяется в задании 2.11.

## Чего здесь не учтено

Основную часть счёта составляют походы в таблицу за найденными строками: около 300 страниц на `t1`, столько же на `t3` и на `t4`. Порядком колонок их не убрать. Убирают их покрывающие индексы, это модуль 7.

## Ловушки

- **`assignee_id` первым.** `t3` читает весь индекс.
- **Одноколоночные индексы.** `t1` читает все 15 тысяч обращений сотрудника ради трёхсот открытых. Счёт около 20 000.
- **`(customer_id)` без `status`.** Почти так же хорошо, но по другой причине. Сам по себе такой индекс заставил бы `t5` читать все 280 обращений клиента ради пяти открытых. Планировщик выкручивается: объединяет его с первым индексом через `BitmapAnd` (модуль 2, шпаргалка) и находит пересечение. Счёт около 904 против 890: проходит, но тратит лишнюю работу на `t5` и держится на том, что планировщик догадался объединить индексы.
- **Три индекса.** Быстро, но бюджет превышен.
