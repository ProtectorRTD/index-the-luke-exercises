# Разбор 2.1

```sql
CREATE INDEX orders_customer_id_status_idx ON orders (customer_id, status);
```

**Было.** `Seq Scan on orders`: прочитана вся таблица, около 10 300 страниц.

**Индекс только по `customer_id`.** Уже намного лучше: `Bitmap Index Scan` находит 499 заказов клиента, но `status` проверяется в `Filter`, и 487 строк выбрасываются. Ради 12 строк прочитано почти 500 страниц таблицы.

**Составной индекс.** В индексе записи отсортированы по клиенту, а внутри клиента по статусу. Отменённые заказы клиента 17 лежат в индексе подряд, спуск по дереву приводит прямо к ним. В плане обе колонки в `Index Cond`, отброшено 0 строк, страниц около 15: 3 на спуск и по одной на каждую найденную строку таблицы.

**Порядок колонок.** Для этого запроса `(status, customer_id)` работает так же хорошо: оба условия — равенства, и любая комбинация двух колонок однозначно задаёт место в индексе. Разница появится, когда тот же индекс должен обслуживать другие запросы. Это задание 2.2.

## Ловушки

- **Индекс по `customer_id`.** Работает, но `status` остаётся filter-предикатом: 487 строк выброшено.
- **Индекс по `status`.** Отменённых заказов во всей таблице 3%, около 30 тысяч. Индекс находит их все, клиент проверяется фильтром.
