# Разбор 1.10

```sql
DROP INDEX orders_status_idx;
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
```

**Причина одной фразой.** Индекс построен по условию, под которое подходит 90% таблицы (900 тысяч строк из миллиона), а отбирает строки второе условие: у клиента 54321 шесть заказов.

**Как это видно.** В плане `Seq Scan on orders`, индекс `orders_status_idx` не используется вовсе. Планировщик оценил: чтобы достать 900 тысяч строк по индексу, придётся прочитать всю таблицу и ещё индекс. Дешевле сразу читать таблицу. Вы считали эту границу в задании 1.7.

**После исправления.** `Bitmap Heap Scan` по `orders_customer_id_idx`: найдено 6 заказов, один из них отброшен фильтром по статусу, прочитано около 9 страниц вместо 10 304.

## Как до этого дойти

1. План показывает, что индекс не используется. Значит, вопрос не «почему индекс медленный», а «почему планировщик считает его невыгодным».
2. `SELECT count(*) FILTER (WHERE status = 'delivered'), count(*) FILTER (WHERE customer_id = 54321) FROM orders;` — 900 000 и 6.
3. Вывод: индексировать нужно `customer_id`.

Ошибка автора первого индекса типичная: колонка взята из `WHERE` без проверки, сколько строк отбирает условие на неё. Индекс по колонке из шести значений, одно из которых занимает 90%, для этого значения бесполезен. Для редкого статуса `pending` тот же индекс работал бы.

## Другие верные решения

Составной индекс `(customer_id, status)` тоже проходит проверку и читает на одну строку меньше. Составные индексы — тема модуля 2.

## Ловушки

- **Добавить второй индекс, не удалив первый.** Запрос быстрый, но бюджет превышен, а бесполезный индекс продолжает замедлять каждую вставку и обновление.
- **Только удалить.** Запись станет дешевле, запрос останется медленным.
