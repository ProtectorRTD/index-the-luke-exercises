# Разбор 2.3

```sql
DROP INDEX events_type_user_id_idx;
CREATE INDEX events_user_id_type_idx ON events (user_id, type);
```

**Было.** `b.sql` использует старый индекс `(type, user_id)` с `Index Cond: (user_id = 54321)` и читает около 3 000 страниц: весь индекс целиком. Та же ловушка, что в задании 2.2.

**Стало.** Индекс `(user_id, type)`:

- `b.sql`: условие на первую колонку, около 16 страниц;
- `a.sql`: обе колонки в `Index Cond`, как и раньше. Для равенства на обе колонки порядок неважен.

Старый индекс после этого не нужен ни одному запросу. Оставлять его значит платить за каждую вставку в журнал без всякой пользы. Цена индексов на запись — тема модуля 10.

Заодно посмотрите на план `a.sql`: там `Index Only Scan`. Для `count(*)` таблица не нужна, всё есть в индексе. Подробно это модуль 7.

## Ловушки

- **Добавить новый индекс и не удалить старый.** Оба запроса быстрые, но индексов на `events` два.
- **Индекс только по `user_id`.** `b.sql` быстрый, но в `a.sql` тип события становится фильтром: у оптовика 17 около тысячи событий, почти все выброшены.
