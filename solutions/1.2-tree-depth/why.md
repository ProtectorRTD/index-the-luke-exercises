# Разбор 1.2

```sql
SELECT root, level FROM bt_metap('orders_created_at_idx');

SELECT live_items FROM bt_page_stats('orders_created_at_idx',
       (SELECT root FROM bt_metap('orders_created_at_idx'))::int);

SELECT s.type, count(*), round(avg(s.live_items)) AS avg_items
FROM generate_series(1, (pg_relation_size('orders_created_at_idx') / 8192)::int - 1) b,
     bt_page_stats('orders_created_at_idx', b) s
GROUP BY s.type;
```

На масштабе `s` получается `level = 2`: корень, один уровень внутренних страниц и листья, глубина 3. Листьев около 2 700, на каждом примерно 370 записей. В корне всего десяток записей: он почти пустой, а внутренние страницы полные.

Отсюда видно, почему дерево неглубокое. Одна внутренняя страница указывает на сотни страниц ниже. Три уровня по ~300 ссылок адресуют 300 × 300 × 370, то есть десятки миллионов записей. Поэтому на масштабе `m` (10 млн заказов) `level` останется 2, а при 100-кратном росте данных добавится максимум один уровень.

`lookup_buffers = level + 2`: `level + 1` страниц индекса на спуск и одна страница таблицы. Это и есть шаги 1 и 3 из главы. Шаг 2, проход по листьям, здесь не нужен: под условие попадает одна строка.

## Частые ошибки

- `depth = level`. Забывают, что сами листья тоже уровень.
- Считают страницы как `pg_relation_size / 8192` целиком. Туда входят служебная страница 0 и внутренние страницы.
