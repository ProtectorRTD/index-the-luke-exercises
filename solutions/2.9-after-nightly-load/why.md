# Разбор 2.9

```sql
ANALYZE refunds;
```

**Причина одной фразой.** Статистика собрана до загрузки: планировщик считает, что строк со статусом `new` нет вообще, ожидает одну строку, идёт по индексу статуса и вместо одной строки читает 100 000, отбрасывая 99 980 фильтром по клиенту.

## Как это видно в плане

```
Index Scan using refunds_status_idx on refunds  (cost=0.42..8.44 rows=1 ...) (actual rows=20 loops=1)
  Index Cond: (status = 'new'::text)
  Filter: (customer_id = 4242)
  Rows Removed by Filter: 99980
  Buffers: shared hit=915
```

Три сигнала:

1. Выбран индекс по `status`, хотя условие на клиента отбирает намного меньше строк.
2. `Rows Removed by Filter: 99980`.
3. Стоимость `8.44` и `rows=1`: планировщик уверен, что это поиск одной строки.

Проверка гипотезы:

```sql
SELECT most_common_vals, most_common_freqs FROM pg_stats
WHERE tablename = 'refunds' AND attname = 'status';
-- {processed,rejected}  {0.9,0.1}   значения new нет

SELECT last_analyze, last_autoanalyze, n_mod_since_analyze FROM pg_stat_user_tables
WHERE relname = 'refunds';
-- статистика собрана до загрузки, с тех пор изменено 100 000 строк
```

По статистике два известных значения занимают 100% таблицы. На долю любого другого остаётся ноль, и планировщик округляет оценку до одной строки. Индекс, который вернёт одну строку, выглядит идеальным.

## После ANALYZE

```
Bitmap Heap Scan on refunds  (... rows=20 ...) (actual rows=20 loops=1)
  Recheck Cond: (customer_id = 4242)
  Filter: (status = 'new'::text)
  Rows Removed by Filter: 40
  Buffers: shared hit=62
```

Теперь планировщик знает, что `new` — треть таблицы, а у клиента 60 заявок. Он идёт по индексу клиента: 62 страницы вместо 915.

Это случай из раздела [Slow Indexes, Part II](https://use-the-index-luke.com/sql/where-clause/the-equals-operator/slow-indexes-part-ii): подходящих индексов два, и выбор между ними делается по статистике.

## Почему это бывает в жизни

Обычно статистику обновляет автовакуум: он запускает `ANALYZE`, когда в таблице изменилось больше 10% строк. Но он работает с задержкой и может не успеть между массовой загрузкой и первым запросом. В нашем стенде автовакуум выключен, чтобы планы были воспроизводимыми.

Практическое правило: после массовой загрузки, большого `UPDATE` или `DELETE` запускайте `ANALYZE` по таблице явно, последней строкой того же скрипта.

## Ловушки

- **Удалить индекс по статусу.** Планировщику останется индекс по клиенту, и запрос ускорится. Но оценка по-прежнему неверна, и следующий запрос со `status = 'new'` снова получит плохой план. Плюс индекс был кому-то нужен.
- **`VACUUM` без `ANALYZE`.** Обновляет сведения о размере таблицы, но не распределение значений в колонках.
- **Составной индекс `(customer_id, status)`.** Запрос станет быстрым, но это лечение симптома: на каждую ошибку оценки индексов не напасёшься.

## Что вынести

Когда план выглядит странно, первым делом сравните оценку строк с фактом. Расхождение в сотни раз означает, что планировщик решал другую задачу. Чинить нужно его исходные данные, а не запрос.
