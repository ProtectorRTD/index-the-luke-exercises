# Разбор 1.3

Числа для масштаба `s`.

| Запрос | Строк | План | Страниц |
| --- | --- | --- | --- |
| Обычный клиент | около 6 | `Bitmap Heap Scan` по индексу | около 9 |
| Оптовики, по умолчанию | около 505 000 (половина таблицы) | `Seq Scan` | около 10 300 |
| Оптовики через индекс | те же | `Index Scan` | около 493 000 |

**Обычный клиент.** Индекс находит несколько адресов, Postgres читает несколько страниц таблицы. Индекс работает так, как задуман.

**Оптовики.** Условие выбирает половину таблицы. `Seq Scan` читает таблицу подряд, каждую страницу один раз: около 10 тысяч страниц.

`Index Scan` проходит по листьям индекса (шаг 2 из главы) и за **каждой** найденной строкой ходит в таблицу (шаг 3). Строки оптовиков разбросаны по всей таблице: их заказы перемешаны с заказами остальных. Поэтому почти каждый поход в таблицу попадает на другую страницу. Полмиллиона строк означают почти полмиллиона чтений страниц, примерно в 48 раз больше, чем `Seq Scan`.

Это и есть «медленный индекс» из главы. Дерево в порядке, спуск занимает 3 страницы. Дорого обходятся проход по листьям и походы в таблицу, когда строк много. Планировщик это знает и по умолчанию выбирает `Seq Scan`: по статистике он оценил, что строк будет половина таблицы.

## Почему Bitmap Heap Scan лучше Index Scan на больших выборках

`Bitmap Index Scan` сначала собирает все адреса, сортирует их по номеру страницы и только потом читает таблицу, каждую страницу один раз. Попробуйте `SET enable_seqscan = off;` без отключения bitmap: страниц будет примерно как у `Seq Scan`, а не 493 тысячи.

## Что вынести

- Индекс выгоден, когда условие выбирает малую долю строк.
- Одинаковый запрос с разными значениями параметра может требовать разных планов. В модуле 3 это вернётся в виде проблемы с подготовленными запросами.
