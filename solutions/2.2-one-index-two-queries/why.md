# Разбор 2.2

```sql
CREATE INDEX orders_customer_id_status_idx ON orders (customer_id, status);
```

Это и есть рецепт из главы: порядок колонок выбирают так, чтобы индекс обслуживал как можно больше запросов. `customer_id` есть в обоих запросах, поэтому он первый.

| Индекс | `q1.sql`, страниц | `q2.sql`, страниц |
| --- | --- | --- |
| `(customer_id, status)` | около 500 | около 15 |
| `(status, customer_id)` | около 2 000 | около 15 |
| без индекса | около 10 300 | около 10 300 |

Числа для масштаба `s`.

**Почему обратный порядок плох для `q1.sql`.** Записи в индексе `(status, customer_id)` отсортированы сначала по статусу. Заказы клиента 17 разбросаны по шести участкам индекса, по одному на каждый статус. Postgres 16 не умеет перепрыгивать между участками. Он всё равно использует индекс, но читает его **целиком**, около 1 560 страниц, и проверяет `customer_id` на каждой записи. В плане при этом написано `Index Cond: (customer_id = 17)`, и это сбивает с толку: условие формально «в индексе», но работает как фильтр по всему индексу. Разоблачает это только число страниц.

Почему Postgres выбрал такой план, а не `Seq Scan`: индекс меньше таблицы (1 560 страниц против 10 300), а проверка записей индекса дешевле, чем строк таблицы.

## Миф о самой селективной колонке

Иногда советуют ставить первой колонку с большим числом разных значений. Для условий на равенство это не имеет значения: оба порядка одинаково хороши для `q2.sql`. Значение имеет только то, какие запросы ещё должны использовать индекс.
