# Разбор 1.5

```sql
SELECT EXISTS (
    SELECT 1 FROM orders
    WHERE customer_id = 17 AND status = 'delivered'
) AS has_delivered;
```

**Было.** `Bitmap Heap Scan` по индексу клиента: все ~500 заказов клиента 17, почти по странице таблицы на каждый, около 500 страниц. Потом `Aggregate` считает их и сравнивает с нулём.

**Стало.** В плане появляется `InitPlan` (подзапрос, который выполняется один раз) с `Index Scan`. `EXISTS` нужна одна строка, поэтому Postgres выбирает обычный `Index Scan`, который отдаёт строки по одной, и останавливается на первом доставленном заказе. Доставлены 90% заказов, так что подходит первый же. Итого: спуск по индексу (3 страницы) и одна-две страницы таблицы.

Обратите внимание, что план поменялся не только из-за остановки. Для `count(*)` выгоден `Bitmap Heap Scan`, потому что нужны все строки. Для `EXISTS` выгоден `Index Scan`, потому что нужна первая. Планировщик учитывает, сколько строк реально потребуется.

## Ловушки

- **`count(*)` во внешнем запросе поверх подзапроса.** Подзапрос без ограничения возвращает все строки, `count` их перебирает. План такой же, как у исходного запроса.
- **`count(*) >= 1`.** Та же работа, другой оператор сравнения.

## Про `LIMIT 1`

`SELECT true FROM orders WHERE ... LIMIT 1` тоже читает одну строку, но проверку не проходит: она прогоняет запрос ещё и на данных, где у клиента 17 нет доставленных заказов. Там он вернёт **ноль строк**, а не `false`. Для кода приложения это разные ответы. `EXISTS` всегда возвращает ровно одну строку.

## Где это встречается в Java

`repository.countByCustomerIdAndStatus(...) > 0` в Spring Data генерирует ровно исходный запрос. `existsByCustomerIdAndStatus(...)` генерирует запрос с ограничением на одну строку.
